# DAL-T-4 개발 일지 — 이동과 회전으로 만든 퍼즐 게임 이야기

> 네이버 카페 게시용 | 작성자: 홍기태 | 2026년 5월

---

안녕하세요! 동아리에서 약 6개월간 혼자 퍼즐 게임을 만들었습니다.  
이름은 **DAL-T-4** — 타일 위를 이동하고 회전하며 퍼즐을 풀어나가는 게임입니다.

아직 완벽하게 완성된 건 아니지만, 지금까지의 개발 과정을 정리해보려 합니다.  
게임 만드는 걸 고민 중인 분들께 조금이라도 도움이 됐으면 좋겠습니다.

---

## 🎮 게임이 뭔가요?

DAL-T-4는 **타일 기반 퍼즐 액션 게임**입니다.

조작법이 특이한데요, 키보드 세 개만 씁니다.

- **F4** — 앞으로 한 칸 이동
- **Left ALT** — 시계방향 90° 회전
- **TAB** — (챕터 4에서 맵 전환)

"단순하네?" 싶지만, 이 세 키의 조합이 꽤 깊어집니다.

예를 들어 `F4 → ALT → ALT`는 "한 칸 이동 후 180° 방향 전환"이고,  
`ALT → ALT → ALT`는 "제자리에서 반시계방향 90° 회전"입니다.

여기에 `F4 → ALT → F4` 같은 조합은 **즉시 게임오버**입니다. (이게 핵심 함정이에요)

단순한 규칙 위에 레벨을 쌓다 보니 꽤 복잡한 퍼즐이 나오더라고요.

---

## 📖 챕터별 개발 과정

### 챕터 1 — 기초부터 천천히

챕터 1은 사실상 튜토리얼입니다. 총 16개 스테이지로 구성했고,  
각 스테이지마다 딱 하나의 새로운 메커닉만 가르칩니다.

| 스테이지 | 처음 가르치는 것 |
|---|---|
| 1-1 | F4로 이동하기 |
| 1-2 | ALT로 방향 바꾸기 (ALT×3 = 반시계 90°) |
| 1-6 | F4-ALT-F4는 죽는다 |
| 1-9 | MoveToggle — 이동 횟수로 발동하는 타일 |
| 1-11 | RotateToggle — 회전 횟수로 발동하는 타일 |
| 1-13 | ActionToggle — 이동+회전 합산 카운팅 |
| 1-16 | 챕터 1 전체 복합 응용 |

레벨 설계에서 가장 신경 쓴 건 **"죽어서 배운다"** 는 철학이었어요.  
텍스트로 설명하는 대신, 자연스럽게 실수하게 만들고  
"아, 그래서 죽었구나"가 즉각 납득되도록 설계했습니다.

예를 들어 1-6은 경로 중간에 방향 전환이 필요한 구간을 배치해서,  
플레이어가 자연스럽게 F4-ALT-F4를 입력하게 유도합니다. 그리고 죽죠.  
"아, 이 순서가 안 되는구나"를 한 번의 사망으로 학습하게 됩니다.

---

### 챕터 2 — 새로운 타일들

챕터 2부터는 타일 종류가 늘어납니다.  
총 25종의 타일 타입이 있는데, 주요 추가 요소는 이런 것들입니다:

- **Ice** — 밟으면 슬라이딩 상태가 됩니다. 관성이 생기는 거죠.
- **Breakable** — 밟을수록 균열이 생기고, 일정 횟수 후 타일이 소멸합니다.
- **Teleport** — StartTeleport와 EndTeleport를 ID로 연결해서 순간이동 구현.
- **ColorToggle** — 색상 기반으로 여러 Toggle을 동시에 제어합니다.

챕터 1이 "기초 문법"이라면, 챕터 2는 "문법 응용"이라고 보시면 됩니다.  
새 타일이 나올 때마다 챕터 1과 같은 흐름으로 — 소개 → 함정 → 우회 — 설계했습니다.

---

### 챕터 3 — 복합 응용

챕터 3은 챕터 1~2에서 배운 모든 메커닉을 섞습니다.  
단일 메커닉 퍼즐이 아니라, 두 가지 이상을 동시에 다뤄야 하는 스테이지가 등장합니다.

ColorToggle이 본격적으로 활약하기 시작하는 챕터이기도 합니다.  
특정 색상의 타일을 밟으면 같은 색의 ToggleTargeted 타일들이 동시에 반응하는 구조인데,  
이걸 이용해서 "순서대로 밟아야 하는 퍼즐"이나 "실수하면 되돌릴 수 없는 퍼즐"을 만들 수 있었습니다.

---

### 챕터 4 — 듀얼맵 시스템

챕터 4는 가장 도전적인 작업이었습니다.

**ALT+TAB**이라는 새로운 조작이 추가됩니다.  
Map1과 Map2, 두 개의 맵이 같은 화면에 겹쳐있고,  
ALT+TAB을 누르면 현재 위치 그대로 다른 맵으로 전환됩니다.

예를 들어 Map1에 적이 있을 때 ALT+TAB으로 Map2로 전환하면 추적을 피할 수 있습니다.  
Map1의 적은 Map1에 있는 플레이어만 추적하거든요.

구현 측면에서도 복잡했습니다.  
Map1과 Map2는 각각 독립적으로 회전하고, Toggle도 독립적으로 작동해야 합니다.  
기존 코드 구조를 꽤 많이 리팩토링해야 했어요.

## 🛠️ 기술적으로 흥미로웠던 것들

### Toggle 시스템 설계

Toggle 시스템은 생각보다 간단한 구조에서 출발했습니다.  
`isToggled`(초기 상태)와 `activationCount`(발동에 필요한 카운트), 딱 두 변수입니다.

- `isToggled=true` + `count=N` → "N번 안에 통과하세요" 타이밍 퍼즐
- `isToggled=false` + `count=N` → "N번 행동하면 문이 열립니다" 경로 퍼즐

이 두 변수의 조합만으로 MoveToggle / RotateToggle / ActionToggle 세 종류가  
완전히 다른 퍼즐 문법을 만들어냅니다.

단순한 시스템이 레벨 디자인의 자유도를 높인다는 걸 직접 체감했습니다.

### ScriptableObject 기반 스테이지 데이터

스테이지 정보(사용 가능한 키, 맵 구성, 클리어 조건 등)를  
`SO_StageData`라는 ScriptableObject로 관리합니다.

덕분에 코드 수정 없이 에디터에서 스테이지 데이터를 수정할 수 있고,  
버전 관리도 훨씬 깔끔해졌습니다.

### 클리어 시퀀스와 UI 시스템

클리어 후 연출 — 결과 표시, 스테이지 정보, 미션 달성 현황 — 을  
`ClearSequenceCompleted` 이벤트로 구동합니다.

`StageInfoPanel` → `BaseInfoPanel` 상속 구조로  
StageNode, Game_PauseCanvas 등에서 공통 로직을 공유하도록 리팩토링했습니다.

## 🌟 Star 시스템에 대해

게임에 Star 수집 요소가 있습니다.  
각 스테이지마다 Star 타일이 있고, 일반 클리어보다 더 어려운 경로에 배치됩니다.

설계 원칙은 하나입니다:  
**"이 Star를 얻으려면 플레이어가 무엇을 추가로 이해해야 하는가"를 먼저 결정하고 배치한다.**

Star를 그냥 경로 위에 놓으면 의미가 없습니다.  
Star는 "클리어했지만 Star는 못 땄다 → 다시 도전"이라는 재도전 동기이자,  
메커닉을 더 깊이 이해하게 만드는 학습 장치여야 한다고 생각했습니다.
